# 御文データ設計

## 目的

御文データは、編集部が制作した「今日の御文」をAndroidアプリへ届けるためのデータ形式を定義する。

御文v1ではデータベースを使用せず、JSONファイルとして管理する。

---

# 設計方針

## 🚀 v1

御文は「毎日発行される一冊」として扱う。

そのため、1日分の御文データを1つのJSONファイルで表現する。

---

## データの考え方

```
今日の御文

├── 表紙
│   ├── 日付
│   ├── 今日のひとこと
│   └── 今日のサマリ
│
├── 本文
│   └── 記事一覧
│       └── 記事詳細
│
└── 今日の持ち帰り
```

---

# JSON構造

## 基本構造

```
{
  "date":"2026-08-01",
  "headline":"AIは書くから働くへ",
  "summary": ["AI活用がQA現場へ広がっています","企業ではレビュー工程の変化が起きています","今日はAIとの協働方法を考えます"
  ],
  "articles": [],
  "takeaway":""
}
```

---

# データ項目

## 表紙情報

## date

### 内容

発行日。

例：

```
"date":"2026-08-01"
```

---

## headline

### 内容

今日のひとこと。

目的：

- 今日読むテーマを決める
- 雑誌の表紙になる

例：

```
"headline":"AIは書くから働くへ"
```

---

## summary

### 内容

今日のサマリ。

3行程度。

目的：

30秒で今日の流れを理解する。

---

# 記事情報

## articles

今日読むべき記事一覧。

🚀 v1では3本。

---

記事構造：

```
{
  "title":"",
  "source":"",
  "url":"",
  "badge":"",
  "theme":"",
  "editor_comment":"",
  "summary":"",
  "why_important":"",
  "qa_application":"",
  "today_action":""
}
```

---

# 記事項目

## title

記事タイトル。

---

## source

情報源。

例：

```
"source":"GitHub Blog"
```

---

## url

原文URL。

---

## badge

記事の状態。

候補：

- 🆕 新着
- 🔄 続報
- 🌍 潮流

---

## theme

テーマ名。

例：

```
"theme":"AIレビュー運用"
```

---

## editor_comment

編集部コメント。

目的：

「なぜ掲載したか」を伝える。

---

## summary

編集部の要約。

目的：

何が起きたか理解する。

---

## why_important

なぜ重要か。

目的：

仕事への影響を理解する。

---

## qa_application

仕事へ持ち帰る内容。

目的：

QA視点へ変換する。

---

## today_action

今日の一歩。

目的：

読むだけで終わらせない。
