# 詳細設計

## 目的

Scoutは、毎朝9:00に世界中の技術情報を収集し、Editorが編集に利用する記事候補を生成する。

Scoutは記事を編集しない。

> **編集部がより良い判断をするための素材を集め、記録すること**を目的とする。
> 

---

# 設計方針

## 🚀 v1

無料で継続できる構成を採用する。

優先事項

- 毎日安定して実行できる
- 情報源を簡単に追加できる
- 記事候補を履歴として残す
- Editorが比較しながら編集できる

---

# 実行フロー

```
毎朝9:00

↓

GitHub Actions

Scout起動

↓

↓

各情報源から記事取得

↓

↓

```

# 情報源設定

取得対象は `sources.json` で管理する。

情報源を追加・削除する場合は、このファイルのみを編集する。

---

# 情報取得

Scoutは情報源ごとに取得処理を持つ。

例

- RSS
- GitHub API
- 公開API

取得した記事は、すべて共通のArticle形式へ変換する。

---

# Articleモデル

Scout内部では、すべての記事を共通フォーマットで扱う。

保持する情報

- タイトル
- URL
- 情報源
- 公開日時
- カテゴリ
- 要約（取得できる場合）

---

# 正規化

情報源ごとの違いを吸収する。

例

- `published_at`
- `pubDate`

など異なる項目名を、

```
publishedAt
```

へ統一する。

Editorは情報源を意識せず記事を扱える。

---

# 重複除外

同じ記事を複数回取得しないようにする。

判定順

1. URL一致
2. タイトル一致

一致した記事は1件だけ保持する。

---

# 記事候補の保存

Scoutは毎日の記事候補を履歴として保存する。

構成

```
archive/

2026-08-01.json
2026-08-02.json
2026-08-03.json
```

また、

```
latest.json
```

には最新の候補一覧を保持する。

---

# 履歴を残す目的

記事候補の履歴は、編集判断を支援するために利用する。

例

- 昨日も候補だった記事か
- 続報として扱うべきか
- 同じテーマが続いているか
- 一時的な話題か、潮流か

Scoutは判断しない。

比較材料を残すことだけを担当する。

---

# Editorへの引き渡し

Editorへ渡すもの

- 最新の記事候補一覧（latest.json）
- 過去の記事候補履歴（archive）

これによりEditorは、

「今日だけ」ではなく、

**数日間の流れ**を見ながら編集できる。

---

# エラー処理

情報源ごとに独立して処理する。

一つの情報源が失敗しても、

他の情報源の取得は継続する。

エラーはログへ記録する。

---

# ログ

毎回以下を記録する。

- 実行日時
- 取得件数
- エラー件数
- エラー内容

ログは障害調査を目的とする。

---

# GitHub Actions

毎朝9:00に実行する。

処理

```
Schedule

↓

Scout

↓

archiveへ保存

↓

latest更新

↓

Commit
```

# 完成条件

Scoutは以下を満たす。

- 毎朝9:00に自動実行される
- 複数の情報源から記事を取得できる
- 共通フォーマットへ変換できる
- 重複を除外できる
- 当日の記事候補を生成できる
- 記事候補を履歴として保存できる
- Editorが過去との比較を行える
- 無料構成で継続運用できる
